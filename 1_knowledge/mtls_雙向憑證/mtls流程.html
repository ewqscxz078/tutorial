mTLS 流程：誰出示、誰驗證、誰設定？

整理日期：2026/11/06（臺灣時間）

mTLS＝TLS 連線的兩端，都以憑證驗證彼此身分。
放好 keystore、truststore 是準備材料；接收端還要啟用用戶端憑證驗證。若要求「沒有用戶端憑證也不能連入」，就必須設為強制要求。標準底層負責執行檢查，不需 API 業務程式逐項重寫。

以下以完整新 TLS 握手、標準憑證驗證、以 CA 為信任來源說明。實際 TLS 訊息順序依協定版本而異；既有連線或 session 恢復不一定重新交換完整憑證。

① 雙方先準備什麼？

來源：MyData（TLS 用戶端）

我方 keystore：我是誰
  • 我方私鑰：留在我方，不交給中信。
  • 我方用戶端憑證：本案須允許 clientAuth。
  • 該憑證的對應中繼鏈。
我方 truststore：我信任誰

用來驗證中信伺服器憑證的信任來源，例如適當的根 CA。

我方設定：讓 HttpClient 的 SSLContext 載入這些材料，使用正常的伺服器憑證及主機名稱驗證。

目的：中信（TLS 接收端）

中信 keystore：中信是誰
  • 中信伺服器私鑰：留在中信。
  • 中信伺服器憑證：允許 serverAuth。
  • 該憑證的對應中繼鏈。
中信 truststore：中信信任誰

用來驗證我方用戶端憑證的信任來源，例如經雙方確認的根 CA。

中信設定：啟用並強制用戶端憑證驗證，且使用正常的憑證驗證機制。

材料對應：我方 keystore 的憑證 → 中信以自己的 truststore 驗證；中信 keystore 的憑證 → 我方以自己的 truststore 驗證。

keystore／truststore 在此表示用途；不同產品可能使用 PEM 檔、JKS、PKCS12、雲端憑證服務等。通常由出示方送中繼鏈，驗證方保存信任根；不必把所有中繼都匯入成獨立信任錨點。若直接信任終端憑證，驗證路徑可能不同。

② 一次呼叫，誰驗誰？

圖中「底層自動」指使用標準驗證機制；CRL／OCSP 廢止檢查仍須另外確認設定。我方也應核對中信主機名稱；本案現有 NoopHostnameVerifier 關閉此項核對。

沒有要求用戶端憑證會怎樣？
即使我方 keystore 裡有憑證與私鑰，中信未要求，我方通常不會主動出示用戶端憑證；可能只完成一般單向 HTTPS。
選填與強制：setWantClientAuth(true) 會要求但允許不提供；若此次有提供且雙方驗證成功，此次連線仍可有雙向驗證，但服務未強制所有連線使用 mTLS。

③ 哪些自動做，哪些要設定或另外寫？

動作負責方處理方式
備妥並載入自己的私鑰、憑證鏈及信任來源雙方工程師／維運需設定檔案、密碼、格式、載入位置；不是檔案放在目錄就會生效。
強制要求用戶端憑證中信 TLS 接收端需啟用設定，例如 need／require／verify 等產品選項。
憑證出示、私鑰持有證明雙方 TLS 元件底層自動執行握手。
憑證鏈、簽章、有效期、CA 限制與演算法限制接收憑證的一方標準底層自動；直接信任項目與自訂驗證可能有差異。
serverAuth／clientAuth 用途檢查我方驗中信／中信驗我方標準底層自動；不需業務程式再手寫一次。用途欄位缺省的規則不同於「明確只有 serverAuth」；本案新憑證屬後者。
中信網址與伺服器憑證名稱核對我方 HTTPS 用戶端一般 HTTPS 由函式庫處理；原生 TLS 需確認設定。本案現有 NoopHostnameVerifier 關閉了這項核對。
憑證是否廢止：CRL／OCSP接收憑證的一方需另確認／啟用。標準 Java PKIX 以 keystore 初始化時預設停用；通常用內建機制，不需自寫整套查詢。
只允許 MyData 身分、憑證或公開金鑰綁定中信額外授權設定或程式；信任某個 CA 不等於只授權 MyData。
API Token、參數、業務權限API 程式另行設定或撰寫業務邏輯，與 TLS 驗證分開。

④ 接收端在哪裡啟用 mTLS？

先找「外部 TLS 連線在哪裡終止」。就在那個元件設定用戶端驗證。不一定是 API 的 Java 程式；以下是選擇之一，無須每一種都設定。

接收方式設定位置／方法誰驗證我方？
Java 原生 TLSSSLServerSocket.setNeedClientAuth(true)；也可用伺服器模式的 SSLSocket、SSLEngine，或將已設 needClientAuth 的 SSLParameters 套用到實際接收元件。搭配正確 SSLContext／TrustManager。Java JSSE／TrustManager。
Java Web Server／應用伺服器在 HTTPS Connector／SSL 設定中選擇「要求用戶端憑證」，載入伺服器身分與用戶端信任來源。設定名稱依產品與版本不同。Tomcat、Jetty 等伺服器使用的 TLS 元件。
Nginx 反向代理ssl_verify_client on; 並設定 ssl_client_certificate；搭配伺服器憑證、私鑰與適當鏈深度。Nginx／OpenSSL。
API Gateway在對外網域／Listener 啟用 mTLS，指定用戶端 CA 信任材料。例：AWS API Gateway 的自訂網域 mutual TLS 與 truststore。另須避免可繞過 mTLS 的其他入口。Gateway，後端可專注 API 授權。
負載平衡器在 HTTPS Listener／SSL Profile 啟用用戶端驗證並設定信任材料。例：AWS ALB 的 mTLS verify 模式。負載平衡器的 TLS 元件。

兩種常見架構

架構 A：Java 直接接收 TLS
MyData ── mTLS ──→ 中信 Java／HTTPS Server ──→ API 業務邏輯
                       ↑ 在這裡要求、驗證我方憑證

架構 B：前方設備接收 TLS
MyData ── mTLS ──→ 中信 Gateway／負載平衡器 ── HTTP 或另一條 TLS ──→ Java API
                       ↑ 在這裡要求、驗證我方憑證
                         後端不一定再寫 setNeedClientAuth(true)

架構 B 的前後兩段是不同連線。前端驗證成功的用戶端身分可由受信任的轉送機制交給後端，後端不能任意相信外部可偽造的身分 Header。若設備只做 TCP/TLS 透傳，TLS 仍由後端終止，就應在後端啟用驗證。

注意產品術語：AWS ALB 的「mTLS passthrough」是將用戶端憑證鏈轉交後端、不由 ALB 驗證；與一般 TCP/TLS 原封不動透傳不同。不要只看到 passthrough 就認定憑證已驗證。

Java：關鍵設定示意

// context 已載入：接收端自己的私鑰／憑證，以及標準 TrustManager
SSLServerSocket server = (SSLServerSocket)
    context.getServerSocketFactory().createServerSocket(8443);

server.setNeedClientAuth(true); // 強制要求用戶端憑證驗證

// 收到連線後：
SSLSocket socket = (SSLSocket) server.accept();
socket.startHandshake();       // 底層執行握手與驗證；失敗則丟例外
// 成功後才處理 HTTP／API；資源關閉與錯誤處理另行實作。

Nginx：關鍵設定示意

server {
    listen 443 ssl;
    ssl_certificate     /certs/server-fullchain.pem;
    ssl_certificate_key /certs/server-key.pem;

    ssl_client_certificate /certs/trusted-client-ca.pem;
    ssl_verify_client on;   # 強制驗證用戶端憑證
    ssl_verify_depth 5;      # 示意值，依實際 CA 鏈設定

    # 後端轉送、授權及 CRL／OCSP 等另行設定
}

⑤ 套回 MyData 本次 TWCA 憑證問題

目前舊憑證

ExtendedKeyUsages [
  serverAuth
  clientAuth
]

若程式讀取的 keystore 未更新，完整握手仍可能送出這張舊憑證。今天 HTTP 200，可能表示它仍被接受；但須看收到的序號與 TLS 驗證紀錄確認。

新網站憑證

ExtendedKeyUsages [
  serverAuth
]

明確缺少 clientAuth。若用它替換用戶端憑證，標準用戶端用途驗證應拒絕。不能以舊憑證目前成功，推論新憑證也可用。

未到期 ≠ 未廢止；公私鑰相同 ≠ 所有驗證都通過。
目前成功不能證明中信沒驗 clientAuth，因為舊憑證本來就有；也不能證明已查過中繼廢止。需請中信確認實際收到的我方序號、TLS 驗證位置、信任規則及 CRL／OCSP 設定。

本案後續：向 TWCA 取得適用 clientAuth 的我方憑證及完整對應鏈，確認與私鑰相符，再更新我方 keystore；中信同步確認信任與授權設定，最後以新連線實測。

⑥ 回想時只問這四題

  1. 誰連誰？MyData 是用戶端，中信是接收端。
  2. 身分材料在哪？自己的私鑰與憑證在自己的 keystore；驗對方的信任依據在自己的 truststore。
  3. 哪裡要求雙向驗證？中信對外 TLS 終止點必須啟用用戶端憑證驗證；要禁止單向連線就設強制。
  4. 額外確認什麼？廢止檢查、身分授權、憑證綁定、實際收到的憑證，以及是否有其他可繞過入口。
