Maven 多模組與跨 Repository CI/CD 架構整理

1. 整體 Repository 分類

建議將 Git Repository 依照「可被其他專案依賴的 Framework/Library」與 「實際可部署的 Spring Boot Application」分成兩大類。

1.1 Framework / Dependency Repository

framework_repo/
├─ pom.xml
├─ PARENT/
├─ CORE/
├─ SDK/
├─ MODULE/
└─ STARTER/

此 Repository 主要產出 Maven artifacts，供其他 Spring Boot Application 引用。

  • PARENT：統一 Maven parent 設定
  • CORE：整個自訂 Spring Boot Framework 共用核心
  • SDK：可獨立使用的 SDK / Library
  • MODULE：Spring Boot 整合模組
  • STARTER：提供 Application 直接引用的 Starter

1.2 Application / Service Repository

service_repo/
├─ xxx_service/
├─ yyy_service/
└─ zzz_service/

此 Repository 主要產出可部署的 Spring Boot Jar。 各 Service 會透過 Maven Repository 引用 framework_repo 所發布的 artifacts。

命名建議：
比起 dependency_repo / jar_repo，更建議採用： 
framework_repo
service_repo
或： 
spring-platform
spring-services
因為兩邊實際上都可能會產生 jar。

2. 同一 Git Repository 的 Maven Reactor 設計

同一個 Git Repository 內，如果這些 Maven modules 屬於同一組產品、 一起維護，而且本來就具有 Maven dependency 關係， 建議由最上層 root pom 統一宣告所有 modules。 

framework_repo/
├─ pom.xml     ← 唯一主要 Reactor Aggregator
├─ PARENT/
├─ CORE/
├─ SDK/
├─ MODULE/
└─ STARTER/

例如：

<packaging>pom</packaging>

<modules>
    <module>PARENT/my-spring-boot-parent</module>

    <module>CORE/my-spring-boot</module>
    <module>CORE/my-spring-boot-starter</module>
    <module>CORE/my-spring-boot-starter-autoconfigure</module>

    <module>SDK/my-logback</module>
    <module>SDK/my-security</module>
    <module>SDK/my-system</module>

    <module>MODULE/my-logback-mdc-spring-boot</module>
    <module>MODULE/my-security-spring-boot</module>
    <module>MODULE/my-system-spring-boot</module>

    <module>STARTER/my-logback-mdc-spring-boot-starter</module>
    <module>STARTER/my-security-spring-boot-starter</module>
    <module>STARTER/my-system-spring-boot-starter</module>
</modules>
CORE / SDK / MODULE / STARTER 比較適合當「目錄分類」， 不一定要再各自建立一層 aggregator pom。

3. 不建議用 Profile 來代表模組分類

原先可能設計： 

-Pparent
-Pcore
-Psdk
-Pmodule
-Pstarter
-Pfull

但若這些模組本來就是同一套 Framework 的完整 Reactor， 則不建議把 module 是否加入 build graph 交給 Profile。

更自然的方式是： 

./mvnw clean install

即代表完整 Reactor Build。

局部 build 則使用 Maven Reactor 原生功能： 

./mvnw clean install \
  -pl :my-security-spring-boot-starter \
  -am

其中：

  • -pl：指定要 build 的 project
  • -am：自動一起 build 該 project 所需要的 upstream modules

如此 Maven 會依 dependency graph 自行判斷： 

my-security-spring-boot-starter
        ↓
my-security-spring-boot
        ↓
my-security
        ↓
my-spring-boot
建議原則：
目錄負責分類、POM dependency 負責依賴關係、 Maven Reactor 負責 build order， 不要用 Profile 再重新描述一次模組關係。

4. CI/CD 不應自行重算 Maven Dependency Graph

如果 CI/CD Script 現在會： 

讀取每個 pom
→ 找 dependency
→ 判斷是否同 repo
→ Recursive 找 dependency
→ 去重
→ 計算 build order
→ 再呼叫 Maven

這等於在 CI/CD 裡重新實作一套不完整的 Maven Reactor。

此做法常會逐漸遇到：

  • parent
  • dependencyManagement
  • BOM
  • property version
  • optional dependency
  • scope
  • profile
  • relativePath
  • plugin dependency

模組越多，Script 越慢且維護成本越高。

建議責任切分

Git Diff
   ↓
判斷 Changed Module
   ↓
------------------------------
以上由 CI/CD 負責
------------------------------
   ↓
Maven Reactor
   ↓
dependency graph
   ↓
build order
   ↓
------------------------------
以上由 Maven 負責
------------------------------

例如 CI 只需要算出： 

:my-security
:my-system-spring-boot

然後： 

./mvnw clean install \
  -pl :my-security,:my-system-spring-boot \
  -am

5. 跨 Repository Dependency 的處理方式

如果 B module 位於另一個 Git Repository， 它就不屬於 A Repository 的 Maven Reactor。

不建議使用： 

<module>../repo-b/my-module</module>

因為這會把 build 綁定特定 checkout 目錄結構。

正確方式是： 

framework_repo
     ↓
mvn deploy
     ↓
Maven Repository
     ↓
service_repo
     ↓
dependency artifact

例如 Application： 

<dependency>
    <groupId>com.mycompany</groupId>
    <artifactId>my-security-spring-boot-starter</artifactId>
    <version>${my-framework.version}</version>
</dependency>
責任界線： 
同 Repo Dependency
→ Maven Reactor

跨 Repo Dependency
→ Maven Repository + Version Management + CI/CD Orchestration

6. Redmine Issue 與 Git Branch 的關係

不建議限制： 

一張 Redmine Issue
只能修改一個 Git Repository

因為實際需求很可能同時需要修改 Framework 與 Application。

例如：

Redmine #12345
    │
    ├─ framework_repo
    │    └─ issue/12345
    │
    └─ service_repo
         └─ issue/12345

因此建議：

  • 一張 Issue 可以跨多個 Repository
  • 每個 Repository 各自建立對應 Branch
  • 每個 Repository 各自有 Commit / PR / CI
  • 由 Issue ID 串起跨 Repo 的 Change Set

若該 Repository 沒有實際修改，則不需要產生 PR。

7. 建議 Redmine 增加 Affected Repositories

若 Redmine 已經會自動建立 Branch， 可增加欄位： 

Affected Repositories

☑ framework_repo
☑ service_repo

例如只改 Application： 

☐ framework_repo
☑ service_repo

則只建立： 

service_repo/issue/12345

如果兩邊都需要修改： 

☑ framework_repo
☑ service_repo

則建立： 

framework_repo/issue/12345
service_repo/issue/12345

8. CI/CD Pipeline 分層

建議分成三種責任：

Pipeline 主要責任
Framework Repo Pipeline Build、Test、Deploy Maven Artifact
Service Repo Pipeline Build、Test、Package Spring Boot Jar
Cross-Repo Orchestrator 協調 Framework 與 Service 的先後順序

9. Framework Repo Pipeline

framework_repo
      │
      ▼
Maven Reactor
      │
      ▼
Compile
      │
      ▼
Unit Test
      │
      ▼
Package
      │
      ▼
Deploy
      │
      ▼
Maven Repository

完整 Build： 

./mvnw clean deploy

局部 Build： 

./mvnw clean deploy \
  -pl :my-security-spring-boot \
  -am

10. Service Repo Pipeline

service_repo
     │
     ▼
Resolve Framework Dependency
     │
     ▼
Compile
     │
     ▼
Unit Test
     │
     ▼
Package
     │
     ▼
Spring Boot Jar
     │
     ▼
Deploy

11. Cross-Repo Orchestrator Pipeline

當同一張 Redmine Issue 同時修改 Framework 與 Service 時， 由 Orchestrator 負責順序。 

Redmine #12345
        │
        ▼
Cross-Repo Orchestrator
        │
        ├─ framework_repo/issue/12345
        │          │
        │          ▼
        │        Build
        │          │
        │          ▼
        │   Publish Temporary Artifact
        │
        │          │
        │          ▼
        └─ service_repo/issue/12345
                   │
                   ▼
             Resolve Artifact
                   │
                   ▼
                 Build
                   │
                   ▼
            Integration Test
                   │
                   ▼
               Package Jar

12. Issue 專用 Snapshot Version

跨 Repo 開發時，不建議直接發布正式版本。

可採 Issue-specific Snapshot，例如： 

1.5.1-issue.12345-SNAPSHOT

流程： 

framework_repo/issue/12345
        │
        ▼
1.5.1-issue.12345-SNAPSHOT
        │
        ▼
Maven Repository
        │
        ▼
service_repo/issue/12345
        │
        ▼
Build / Integration Test

正式 Merge 後再發布： 

1.5.1

13. Service POM 不一定要 Commit Snapshot Version

Application POM 可以保持正式 baseline： 

<properties>
    <my-framework.version>1.5.0</my-framework.version>
</properties>

Issue Build 時由 CI Override： 

./mvnw clean package \
  -Dmy-framework.version=1.5.1-issue.12345-SNAPSHOT

如此可以避免大量只有版本變更的暫時性 Commit。

14. 跨 Repo Merge 順序

如果 dependency direction 是： 

framework_repo
       ↓
service_repo

則正式 Merge 順序建議： 

1. Merge framework_repo
        ↓
2. Publish正式 Maven Artifact
        ↓
3. service_repo 切換正式 Framework Version
        ↓
4. Build / Test
        ↓
5. Merge service_repo
不建議讓 service_repo 先 Merge， 否則 main branch 可能引用一個尚未發布的 Framework Version， 造成正式分支 Build 失敗。

16. 各元件責任界線

元件 責任
Directory 原始碼與職責分類
Root Aggregator POM 定義同一 Repo 的 Maven Reactor
Maven Dependency 定義 Module 之間的依賴關係
Maven Reactor 決定 Build Graph 與 Build Order
Maven Repository 處理跨 Repository Artifact Boundary
Redmine 定義需求與 Change ID
Git Branch 各 Repository 的實際 Change Set
Repo Pipeline 單一 Repository 的 Build/Test/Package
Cross-Repo Orchestrator 協調多 Repository 的 Build 與 Artifact 先後順序
Deployment Pipeline 環境部署、驗證與 Rollback

17. 最終建議摘要

  1. 同一個 Git Repository 內，建立一份主要 Root Aggregator POM， 統一宣告所有 Maven Modules。
  2. CORE、SDK、MODULE、STARTER 保持為目錄與職責分類， 除非真的有獨立 Build Lifecycle，否則不必另外建立 Aggregator POM。
  3. 不建議使用 Maven Profile 模擬 CORE / SDK / MODULE / STARTER 的 dependency graph。
  4. 同 Repo 的 dependency/build order 應交給 Maven Reactor 處理。
  5. CI/CD 只需負責找出 Changed Module， 再搭配 -pl / -am。
  6. 跨 Repository 的依賴透過 Maven Repository 與 Artifact Version 管理。
  7. 一張 Redmine Issue 可以同時修改多個 Repository。
  8. 各 Repository 各自有 Branch / PR / CI， 但使用同一 Issue ID 串聯。
  9. 跨 Repo 的 Build 順序交由 Orchestrator Pipeline 協調。
  10. 跨 Repo Issue 測試可使用 Issue-specific Snapshot Version。
  11. 正式 Merge 時應遵守 Dependency First： Framework 先發布，Service 再切正式 Version 並 Merge。

18. 一句話總結

同 Repo 的依賴關係交給 Maven Reactor， 跨 Repo 的依賴關係交給 Maven Repository， 需求關聯交給 Redmine， 跨 Repo 的先後順序交給 CI/CD Orchestrator。
